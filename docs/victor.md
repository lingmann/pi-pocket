# On-device Victor

Victor is an experimental, English-only conversation mode that recognizes speech and reads Pi's replies on your device. Only recognized text goes to Pi Pocket; audio stays local. Pi's replies still require a network connection. The ordinary dictation mic beside Send is separate and may use a browser-provided speech service.

## Setup

**Installation support:** Run this fork from a checkout using the setup below. npm, Nix, NixOS, and Docker/Podman packaging is retained from upstream but is not adapted or supported for this fork, including Victor's speech assets and fork-specific build checks. The upstream npm package and container image do not include Victor's preparation script, source pins, or prepared speech assets.

On the server, prepare the pinned speech assets:

```sh
just prepare-victor
```

Without `just`, run `node scripts/victor/prepare-victor-assets.mjs` from the repository root. Assets are stored under ignored `vendor/victor/`. Rerunning preparation verifies existing assets and skips downloads when they are valid and unchanged; otherwise it rebuilds them.

`just start`, `just start-local`, and `just dev` prepare assets automatically. `just dev` uses Tailscale HTTPS port 8444 forwarding to loopback port 8788, with separate Pocket data under `~/.pi-pocket-dev` but the same host Pi authentication credentials and model configuration as regular Pi Pocket; see [development launch details](../README.md#https-with-tailscale-serve).

Open Pi Pocket over HTTPS (localhost also works) and allow microphone access. Keep the page visible and the phone unlocked. Safari on iPhone 13 Pro Max with iOS 27 or newer is the target, but physical-device audio and long-session reliability are not yet qualified.

## Using Victor

1. Open an idle main session, select a model, and clear the message queue. You can keep ordinary text in the composer, but must send or remove attachments first. You need permission to send and, when taking turns, the driving turn. Victor is unavailable in PiP and subagents.
2. Tap **Victor**. Existing text becomes the starting draft; new speech goes after it, not at the caret. Wait for preparation and the rising recording cue before speaking.
3. End your message with **“send it”**. Victor removes that spoken command and submits the combined draft. Saying only “send it” submits existing text; those words already in the starting draft never trigger a send. Silence never sends.
4. The microphone stops while Pi works and reads its completed answer aloud, then listening resumes. Speaking over playback is not supported.

**Read reply** replays the latest answer while listening. **Speed** changes subsequent speech and is saved in this browser; the default is 1.25×.

Turn Victor off to stop local audio and return the complete unsent draft to the composer. Edit it, then turn Victor on again to continue without duplicating the earlier text. This preserves the draft, not the audio engine or a playback position, and does not stop Pi's shared run. Ordinary dictation is blocked until Victor is off.

Victor sends ordinary text only. Slash and shell commands, attachments, and file mentions with **Send them along** enabled must use the ordinary composer. Folded pastes expand to their full text in Victor and return expanded when you turn it off. You cannot activate Victor while a typed or Victor submission is still awaiting its HTTP response. After turning Victor off during a send, you can type the next draft, but Send in that conversation stays disabled until the response arrives. You can still send typed messages in other conversations; Victor reactivation stays blocked across the tab.

A draft stays recoverable during preparation and microphone failures. Once sending begins, its composer copy is cleared to avoid duplicate submissions. A definite rejection keeps the unsent text (a late rejection after turning Victor off restores it to its original conversation without erasing newer typing). Uncertain delivery does not automatically restore a sendable copy.

Navigation, leaving the tab, connection loss, permission changes, or competing messages can stop Victor. If submission is uncertain, check the conversation before sending again; Victor does not automatically resubmit.

### Conversational replies

The **Victor reply style** extension is on by default. Its default instruction asks Pi to answer Victor messages conversationally in at most three short sentences, without headings, lists, tables, code blocks, or long URLs. It does not truncate answers or limit tool calls; the model must follow the instruction. The owner can replace the voice instruction with `/victor-style` or disable the extension in **Menu → Extensions** without disabling Victor's audio.

The style follows each submitted message, not the microphone's current state. Turning Victor off does not change an answer already underway. The next typed message, including ordinary dictation into the composer, restores normal style. A queued message changes style only when Pi takes it; a steering message changes it at the next request preparation after placement. PiP and subagents do not use the voice rule.

Victor sends `source: "victor"` with its text. The server records the source before submitting the input, keyed by the existing request ID, and retries keep the first recorded source. The extension reads the latest input placed in the active run, so the style survives tool calls, compaction, and server restarts. A new untagged message, including a scheduled message, background-task completion, or subagent report, uses normal style. There is no separate server-side microphone toggle. Moving a queued message to Interrupt preserves its source and the sources of the other messages queued again behind it. These source records are copied in the same transaction that creates the interrupt task, before any replacement message can run.

The submit response for Victor includes `acceptedText`, the server-prepared text after hidden-value replacement (`host.hide`). The controller checks the transcript against this text only after the response arrives, and still requires its own author attribution and no competing message. This field is not proof of the first submission's content when a request ID is reused; Victor creates a fresh ID for each send and never automatically retries.

#### Configure the voice instruction

On a server running the integrated 0.14 API, the owner can use these native commands in an accessible conversation. They run without asking the model:

| Command                                 | Result                                                                                       |
| --------------------------------------- | -------------------------------------------------------------------------------------------- |
| `/victor-style` or `/victor-style show` | A transcript card marked **Default** or **Custom**, with the complete effective instruction. |
| `/victor-style set <instructions>`      | Replace the voice instruction across the whole Pocket instance.                              |
| `/victor-style reset`                   | Delete the override and restore the code default.                                            |

For example:

```text
/victor-style set This answer will be spoken aloud. Use brief, natural sentences and avoid visual formatting. These reply-style instructions do not limit tool calls or the work needed to answer correctly.
```

`set` takes all remaining text literally, trimming only outer whitespace. Internal spacing, newlines, quotes, backslashes, and apparent file paths are ordinary instruction text; there is no shell parsing, escape decoding, file loading, or flag syntax. The trimmed instruction may contain at most **3900 JavaScript string code units** (`.length`, not bytes or displayed characters). Pocket separately limits all command arguments to 4000 code units. Empty instructions, unknown actions, and extra arguments after `show` or `reset` are rejected without changing the setting.

For a long or multiline paste, type `/victor-style set ` first, then paste only the instruction after it. The existing composer can fold a long paste into a placeholder: if the entire command is inside that placeholder, Pocket sends it as chat instead of executing it. Before sending, check that the command hint says **not sent to Pi**. Long show cards offer **Show all … lines** to reveal the complete text.

The custom instruction **replaces**, rather than supplements, the default. Include any voice constraints you want to keep. Saving the current default explicitly still counts as Custom, so a later code-default change does not alter that choice. The normal-chat instruction stays fixed: it clears Victor's voice restrictions without imposing a style on ordinary conversations.

A successful save or reset gives a short private toast. Changes apply when the next Victor model request is prepared, across conversations, including subsequent tool rounds in an active run. They do not alter a provider request already prepared. Settings changes need no restart, source edit, or speech-asset preparation.

The override survives extension reloads and server restarts. Turning the extension off removes its command and prompt section but keeps the setting; re-enabling restores its use. A command already running may finish under its original module version, so disabling does not undo a committed setting. Concurrent writes take effect in commit order.

If a voice-settings read fails or a stored override is invalid, the extension warns and uses the default voice instruction, never an earlier custom instruction. `show` identifies invalid stored values as falling back to Default; a failed command read or write reports failure instead of success. Source-attribution lookup failures still use the normal-chat reset to avoid leaving voice restrictions active.

Only the owner can invoke this global command; guests, session-limited guests, and viewers cannot. While someone else drives a conversation, the owner can use another accessible conversation. **A show card is visible to everyone who can read that conversation and appears in export and search.** Use an owner-only conversation when that matters. These settings are not a secret store: command arguments and results remain in durable task data, and the effective instruction goes to the model provider. Put no secrets in instructions.

## Downloads and caching

First activation downloads about **149 MB**. Do this on Wi-Fi using the same browser and stable HTTPS address you will use later. Different addresses or browser profiles do not share downloads; changing a quick-tunnel hostname requires another download.

Later activations reuse cached assets but still take time to initialize. Updates may require a fresh download. Browser storage eviction or clearing site data also removes cached models. Victor is not an offline app.

## Updates

**Pi Pocket updates are check-only in this fork.** Menu → **Update Pi Pocket** shows newer upstream releases and their notes for manual review. Checks run 2 minutes after startup and every 6 hours while **Look for new versions** is on. They do not fetch release commits, install packages, change the checkout, or restart the server. The install button stays disabled, the automatic-install setting is absent, and the server rejects installation requests even if an old setting enabled them. These notices compare the incorporated upstream version, not `victor/vX.Y.Z` releases.

Merge upstream through [the fork workflow](fork-workflow.md), then deploy the reviewed fork manually. `PI_POCKET_UPDATES_REPO` can change the discovery source, but cannot enable installation. The upstream update and rollback code remains in place to keep future merges small; Victor does not initiate those updates.

Upstream 0.25.0 adds npm installation, background-task indicators and completion cards, independent subagent thinking levels, and per-model compaction settings. It changes no dependency versions or database format. Victor still requires a fork checkout. Background commands require Linux; their absence on macOS does not disable Victor. Background-task completions use ordinary reply style once their messages enter a run; a queued completion does not change an active Victor reply.

When deploying across 0.23.0, stop and start the complete launcher to load that release's launcher changes; **Restart server** alone does not reload the launcher.

Preparation installs the versions pinned in `victor-sources.json`; it does not choose newer models automatically. Model changes need compatibility testing before use.

After installing an update that changes Victor's server code or assets:

1. Turn Victor off on connected clients.
2. Run `just prepare-victor` in the serving checkout.
3. Have the owner use **Menu → Restart server**, then reload clients before activating Victor.

Pi Pocket 0.21.0 upgrades the database through Pi Durable 1.4.0. Before deploying it, stop the server and back up the complete Pocket data folder. Older Durable versions cannot open the upgraded database.

To roll back code or assets, restore the previous source/code and repeat these steps. Rolling back across the 0.21.0 database upgrade also requires restoring the pre-upgrade data backup with the server stopped. Retained asset directories alone are not a rollback.

## Troubleshooting

- **Assets unavailable / HTTP 503:** rerun preparation on the server. After repair, restart and reload as above. Ordinary chat remains available.
- **Interrupted download:** activate Victor again on a stable connection; completed cached downloads can be reused.
- **Checksum error:** rerun preparation, then delete the affected `pocket-victor-…` cache in browser developer tools and reload. To force a server rebuild, delete `vendor/victor/.prepared.json` before preparing again.
- **Audio failure or stuck mode:** turn Victor off and on. Check microphone permission, HTTPS, and that the page is visible. Check the conversation before repeating a message.

## Maintaining the fork

See [the fork workflow](fork-workflow.md) for shared-main collaboration: squash feature PRs, preserve upstream-update merges, check changes, and tag tested releases. These repository operations are separate from preparing assets and restarting a running app.

### Styling boundary

Keep Victor's markup in `web/victor-controls.js` and its layout in `web/victor.css`. Reuse upstream's documented `button`, `small`, and `error-box` classes, shared icons and spinner, and [theme tokens](extensions/reference/theme-surface.md). The existing stylesheet import stays in the `pocket` layer so user themes can override it. The idle toggle exposes the generic `composer-button` part; it is not a `plan-chip`.

Do not borrow Plan's feature-specific classes or edit shared styling to make Victor look like Plan: those classes also control visibility and layout. A few Victor-owned dimensions and composer-container thresholds are intentional. Keep neighbouring-control overrides together in `victor.css`; they give up thinking-level text before Plan as the composer narrows. The active panel is outside that container and wraps its own controls.

Use token-based surfaces, corners, density spacing, and draft text size. Preserve upstream focus and field styling, and check the idle toggle's expanded touch target as well as the visible button. The controls show one live status, a shared spinner while preparing/sending/waiting, and a shared error box when stopped. Error state still owns the draft until Victor is turned off.

After upstream merges, use the focused composer UI tests to check phone and narrow-desktop layouts, Pocket/Lantern and light/dark colors, density, text size, and keyboard/touch access. Shared primitives and tokens track upstream automatically; Victor's own geometry still needs review when upstream changes the composer. Keep these tests in Victor's test files rather than adding fork assertions to upstream suites.

### Check-only update boundary

`src/server/app.ts` sets the `UpdatesOptions.checkOnly` explanation unconditionally. `src/server/updates.ts` skips release preparation and installation-specific status checks in this mode, reports that explanation as the blocker, and rejects `apply` before discovery or side effects. `src/server/host.ts` exposes the policy to `src/server/extensions/updates.ts`, which omits the automatic-install setting. The existing browser module uses the blocker to disable installation; keep its UI and upstream recovery implementation unchanged.

### Composer handoff boundary

Keep fork-specific lifecycle rules in `web/victor-composer.js`, not in the shared composer. The adapter receives synchronous draft read, expand, and write operations; writing expanded text must clear old paste mappings before notifying a mounted composer. The composer retains its existing storage keys, paste syntax, file-mention detection, and UI setters. Do not copy those formats into the adapter.

The shared composer passes Victor's active state to its button slot so Attach stays disabled during voice ownership. Victor's idle toggle and active controls stay outside the configurable slots; hiding or reordering shared buttons must not remove the way to stop Victor. Ordinary typed messages use the shared Steer, Queue, or Interrupt selection. Victor submissions always use `followUp`, independently of that selection. Extension composer keys run only when Victor does not own the draft. The adapter invalidates delayed editors at each handoff, so an old shortcut cannot overwrite speech even after Victor stops. The shared callback also rejects writes to an unmounted composer or a draft changed since the shortcut began. Upstream retains keyboard dispatch, font/theme resize listeners, and their cleanup.

The controller's `enable` contract documents when validation, consumption, and preservation run. Consumption precedes each POST and throws if the stored draft no longer matches the handed-off copy. Preservation can outlive the originating component: the adapter replaces its predecessor or appends to newer expanded text, then notifies only the mounted composer for that conversation. Uncertain delivery does not restore submitted text. `blocksSend(conversationId)` protects the originating draft while the separate activation guard remains tab-wide.
